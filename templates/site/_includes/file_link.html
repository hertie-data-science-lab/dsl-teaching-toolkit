Right after it sits ONE small chevron (`details.file-menu`), "More ways to open", whose menu lists the SAME four items for every file, in the same order, under two headings: Open view - GitHub Edit in browser - the reader's editor by name An item the file does not have is still listed, greyed (`li.file-menu-off`: a label with `aria-disabled="true"` and no href) with a one-line reason under it, so a reader learns what exists and why this file lacks it rather than finding a menu of a different length on every row. `view` is live only with a hosted copy (`view_url`, which only publish.yml produces), else "Not published on this site". `GitHub` is always live. Both Edit items are written here DISABLED, with the reason Liquid can give: "Not an editable format" for a pdf/pptx/docx/xlsx/zip, else the Profile step each needs - or, on a site with no materials repo (no /profile/, no script), that this site does not edit. They depend on WHO is reading, which a public page cannot know, so `_includes/open_in.html` replaces them from the reader's saved profile: live where it can build the URL, otherwise with the exact reason. A reader without JavaScript keeps what is written here. The format test is a `contains` (no filters inside an `if`, and no `assign` - below); the script's anchored test is the one that decides. A `

Each item is an icon and a label on one line, a one-line description (or reason) under it. `inline` is for a caller that already brackets the link: the Updates box renders each file as `[name]`, and a menu inside a sentence would swamp it. Set it and the file gets what it always had there - a middle dot and the word `GitHub`, and only where there is a hosted copy to tell apart from the name. `url` is the file on GitHub. `view_url` is the semester site's own hosted copy, written by the sync only for a file the course published (publish.yml) that a browser renders - so the NAME opens the copy that renders, and `GitHub` in the menu keeps the file's own home one click away. Every live menu item opens a new tab, and so does the Profile link in a reason: they all leave the page the reader is working through, and `view` in particular is a deck or a pdf they will want beside the list, not instead of it. No `assign` and no `capture`: materials_entry.html includes this from inside its own recursion, and both write to Liquid's outermost scope.
